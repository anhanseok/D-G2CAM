# 1차 연구 실험 설계 — 결정 사항

## 목적지

Real CCTV 영상에 열화를 적용했을 때 교통사고 탐지 AI의 When/Where/What 성능 변화를 분석하는 1차 연구의 **실행 가능한 실험 설계서**.

**이유**: 2차 연구(Synthetic-to-Real)는 1차 결과, 즉 어떤 열화가 치명적인지에 따라 설계가 달라진다. 지금 2차까지 정하면 추측 위에 설계하게 된다. 지도교수 피드백도 "취약성을 먼저 증명하고 두 번째 연구는 후속으로"였다.

## 연구 질문의 성격

사고 유무를 판별하거나 성능이 급락하는 임계점을 찾는 연구가 아니다. **어떤 판단 과업(When/Where/What)이 어떤 열화 요인에 가장 취약한가**를 3단계 열화로 비교하는 연구다.

**이유**
- ACCIDENT 실제 영상은 전부 사고가 들어 있는 영상이라 "유무" 과제가 성립하지 않는다.
- 임계점을 증명하려면 열화 단계를 촘촘히 나눠야 해서 시간이 부족하다. 지도교수도 "성능 붕괴" 표현을 피하라고 권고했다.

## 확정

### 1. 모델: Molmo-7B-D 1개

- **결정**: `allenai/Molmo-7B-D-0924`, zero-shot. 원본과 모든 열화 조건에 같은 설정(프롬프트, 0.5초 간격 프레임 추출, greedy 디코딩, 공식 지표)을 쓰고, 입력 영상만 바꾼다.
- **이유**
  - 원 논문에서 When/Where/What 세 과업의 실제 영상 성능이 **모두 보고된 유일한 모델**이다(When 0.343, Where 0.488, What 0.293). 원본 성능 재현의 기준이 명확하다.
  - 학습이 없는 zero-shot이라 학습 데이터의 화질 분포가 개입하지 않는다. 열화의 영향만 분리해서 볼 수 있다.
  - 모델을 비교하는 연구가 아니므로 1개로 충분하다. GPU 시간은 모델 수에 비례한다.
- **버린 대안**
  - Qwen2.5-VL-7B: 논문에 Where/What 수치가 없어 재현 기준이 약하다.
  - Heuristic(광학 흐름): What 과업이 없다. 여유가 있으면 보조로 추가한다.
  - 상용 API(GPT, Gemini): 비용이 들고 모델 버전이 바뀌어 재현이 어렵다.
- **한계**: 단일 모델 결과라 "Molmo만 약한 것 아니냐"는 반론이 가능하다. 결론의 한계와 후속 연구에 명시한다.

### 2. GPU 환경: VRAM에 따라 분기

- **결정**: 집 PC(RTX 4060 Ti)의 VRAM이 16GB면 집 PC에서 8bit 양자화로, 8GB면 Colab Pro(L4)에서 원본 bf16으로 실행한다.
- **이유**
  - Molmo-7B 원본(bf16)은 약 17GB가 필요해서 8GB로는 4bit밖에 안 된다. 4bit는 원본과의 차이가 커서 논문 수치와 비교하기 어렵다.
  - 16GB면 8bit로 무료로 돌릴 수 있다. 모든 조건을 같은 양자화 모델로 돌리므로 **상대 비교(RPD)는 유효**하다.
  - 작업 PC(Intel Iris Xe)에는 NVIDIA GPU가 없다.
- **미정**: 집 PC의 VRAM 용량 확인

### 3. 평가 데이터: 공식 IID test split 1,520개

- **결정**: ACCIDENT 실제 영상 2,027개 중 공식 IID test split 1,520개를 쓴다.
- **이유**
  - 목표 규모(약 1,600개)와 비슷하다.
  - 임의 표본이 아니라서 "왜 이 영상들인가"를 한 줄로 설명할 수 있다.
  - 충돌 유형 비율을 고려한 층화 분할이라 공식 벤치마크와 직접 비교할 수 있다.
- **실측 특성**([데이터분석_결과](데이터분석_결과.md)): 길이 중앙값 29.9초(99%가 30.1초 이하, 최대 115초), 짧은 변 기준 해상도 중앙값 720p(범위 240p~2160p), 주간 1,034개·야간 486개. Head-on은 90개뿐이라 유형별 분석에서 신뢰구간이 넓어진다.

### 4. 열화 요인: 해상도 저하, 영상 압축, 모션 블러

- **결정**: 3종을 각각 3단계(L1~L3)로 적용한다. 원본을 포함해 총 10개 조건이다.
- **이유**
  - 지도교수 권고 범위(대표 요인 2~3개)에 맞는다.
  - 세 요인이 서로 다른 정보를 손상시켜 과업별 차이가 드러나기 좋다. 해상도는 공간 세부, 압축은 빠른 움직임 구간의 화질, 블러는 움직임 경계를 손상시킨다.
  - 모두 CCTV 운용에서 흔하고, 파라미터로 강도를 정량 제어할 수 있다.
- **제외**: 저조도 (아래 "제외 사항" 참고)

### 5. 해상도 저하 단계: 원본 대비 1/2, 1/4, 1/8

- **결정**: 가로·세로를 원본 대비 비율로 다운샘플한 뒤 원래 크기로 복원한다(bicubic). 단계별 결과 해상도의 중앙값을 함께 보고한다.
- **이유**
  - 1,520개 **전부에 모든 단계를 적용**할 수 있어서 단계 간 표본이 같다. 비교가 공정하다.
  - 압축(원본 비트레이트의 1/2, 1/4, 1/8)과 블러(프레임 폭 대비 %)처럼 세 요인을 모두 **원본 대비 상대 강도**로 통일한다.
- **버린 대안**
  - 규격 해상도 고정(720p/480p/240p): 원본이 720p 이하인 영상에는 L1을 적용할 수 없어서 단계마다 표본 수가 달라진다. 규격과의 대응은 "결과 해상도 중앙값"으로 대신 설명한다.

### 6. 압축 단계: CRF 29 / 35 / 41

- **결정**: H.264(libx264)로 재인코딩한다.
- **이유**
  - 원본 1,520개가 모두 H.264 High이고, **이미 CRF 23 수준으로 균일하게 인코딩**되어 있다. 샘플 40개를 CRF 23으로 재인코딩하면 원본 크기의 96%가 나온다.
  - 그래서 CRF 29/35/41은 **모든 영상에서** 원본 비트레이트의 약 1/2, 1/4, 1/8을 만든다(중앙값 0.51/0.25/0.12, 크기 변화가 없는 영상 0/40). 해상도 단계와 숫자가 대칭이다.
  - CRF는 동영상 강건성 연구의 표준 설정이라 설명하기 쉽다.
- **버린 대안**
  - 원본 비트레이트 비율 방식: 실측해 보니 CRF 방식과 결과가 사실상 같았다. 더 단순하고 표준적인 CRF를 택한다.
- **예비안**: 압축은 눈으로 봐도 변화가 가장 작다. pilot test에서 성능 저하가 거의 없으면 CRF 35 / 41 / 47로 강화한다.

### 7. 저해상도 원본의 L3 처리: 그대로 적용

- **결정**: 원본 해상도와 관계없이 모든 영상에 1/8을 적용한다. 결과는 원본 해상도 그룹별로도 나눠서 보고한다.
- **이유**
  - "모든 영상, 모든 단계" 원칙(5번)이 유지된다.
  - 문제가 되는 360p 이하 원본은 31개(2%)뿐이라 전체 평균에 주는 영향이 작다.
  - 원본 화질 등급별 하위 분석을 어차피 하므로, 원본 해상도 그룹을 추가해도 작업이 거의 늘지 않는다.
- **버린 대안**
  - 하한선(90p) 두기: 비율 원칙이 깨져서 "L3 = 1/8"이라는 설명이 부정확해진다.
  - 360p 이하 제외: 요인마다 표본 수가 달라져서 요인 간 비교가 복잡해진다.
- **논문 기재**: 240p 원본은 L3에서 30p가 되어 사고 장면을 식별할 수 없는 수준이라는 점을 한계 겸 관찰로 적는다.

### 8. 모션 블러 단계: 프레임 폭의 1% / 2% / 4%, 수평 방향

- **결정**: 선형 모션 블러 커널의 길이를 프레임 폭 대비 1% / 2% / 4%로 두고, 방향은 수평으로 고정한다. 프레임마다 같은 커널을 적용한다.
- **이유**
  - 영상마다 해상도가 달라서 픽셀 수로 고정하면 강도가 달라진다. 폭 대비 비율로 두면 세 요인을 모두 원본 대비 상대 강도로 통일할 수 있다(5·6번과 같은 원칙).
  - 블러 길이는 노출 시간 동안 차량이 움직인 거리에 비례한다. 1% → 2% → 4%는 노출 시간이 2배씩 늘어나는 상황에 해당한다.
  - 샘플 확인 결과 세 단계의 차이가 뚜렷하다. 1%에서 번짐이 보이고, 2%에서 세부가 사라지며, 4%에서 차량 윤곽이 거의 사라진다.
  - 방향을 고정하면 "블러 강도"만 변수로 남는다.
- **버린 대안**
  - 영상마다 무작위 방향: 방향이 또 하나의 변수가 되어 해석이 복잡해진다.
  - 차량 진행 방향: 가장 현실적이지만 영상마다 진행 방향을 추정해야 해서 작업이 크다.
- **한계**: 차량이 세로로 움직이는 장면에서는 실제 모션 블러와 다를 수 있다. 논문에 명시한다.

### 9. 하위 그룹 분석: 충돌 유형, 주간/야간, 원본 화질

- **결정**: 추가 추론 없이 결과를 메타데이터로 나눠서 본다.
  - **본문**: 충돌 유형(5종), 주간/야간(1,034 / 486), 원본 화질 3단계(좋음 = Excellent+Good 300 / 보통 = Fine 412 / 나쁨 = Poor+Very Poor 808)
  - **부록**: 원본 해상도(짧은 변 720p 미만 / 이상). L3가 저해상도 원본에 지나치게 센지 확인하는 용도다.
- **이유**
  - 충돌 유형: 지도교수가 요청한 "어떤 사고가 특정 열화에 더 민감한가" 분석이다.
  - 주간/야간: 저조도를 합성하지 않는 대신 실제 야간 영상으로 영향을 보는 대체 분석이다.
  - 원본 화질: 샘플에서 관찰한 천장 효과(원래 나쁜 영상은 열화를 걸어도 변화가 작음)를 검증한다.
  - 원본 화질 5등급은 Excellent가 53개뿐이라 3단계로 묶어 그룹당 표본을 300개 이상으로 맞춘다.
- **버린 대안**
  - 날씨(눈 93개), 도로 형태(8종, 회전교차로 1개): 그룹이 너무 작거나 많아서 해석이 불안정하고 범위가 넓어진다.
- **한계**: Head-on은 90개라 유형별 결과의 신뢰구간이 넓다. 논문에 명시한다.

### 10. 평가 지표와 통계

- **결정**
  - **When**: 공식 가우시안 유사도. 본문은 σ = 1초, 부록은 σ = 0.5초·2초
  - **Where**: 공식 이방성 가우시안 유사도를 두 방식으로 측정한다. (a) 예측 시점 기반(공식 파이프라인), (b) 정답 시점(oracle) 기반
  - **What**: 5종 Top-1 정확도
  - 공식 통합 점수(조화평균)는 참고용으로만 보고한다.
  - **비교**: RPD = (P₀ − P_k) / P₀ × 100%
  - **통계**: 영상 단위로 짝지은(paired) 부트스트랩 95% 신뢰구간(1,000회). "A가 B보다 취약하다"는 신뢰구간이 0을 포함하지 않을 때만 주장한다.
- **이유**
  - 공식 지표를 그대로 써야 원 논문 수치와 비교할 수 있고, 새로 설명할 것이 적다.
  - 공식 파이프라인은 예측 시점의 프레임으로 위치를 판단하므로, When 오류가 Where 점수로 전파된다. oracle 측정이 있어야 위치 판단 자체의 취약성을 분리할 수 있다.
  - 과업마다 원본 점수 수준이 달라서(When 0.343, What 0.293 등) 절대 점수 차이로는 공정하게 비교할 수 없다. 그래서 RPD를 쓴다.
  - 모든 조건에 같은 1,520개 영상이 들어가므로 짝지은 비교가 독립 비교보다 검정력이 높다.
  - 통합 점수는 과업을 섞어 버려서 이 연구의 핵심(과업별 분리)과 맞지 않는다.
- **비용 메모**: Where oracle은 조건마다 정답 시점 프레임 1장으로 위치 추론을 한 번 더 한다. 영상당 이미지 1장이라 전체 추론 시간 대비 추가 부담은 작다. 정확한 시간은 pilot test에서 잰다.

### 11. 실행 시간 관리와 pilot test

- **문제**: 공식 When 파이프라인은 0.5초 간격 프레임마다 모델을 한 번씩 호출한다. 30초 영상 1개에 약 60회이고, 전체는 1,520개 × 10개 조건 × 60회 = **약 91만 회**다. 호출당 0.5~1초(L4, bf16)면 약 130~250시간, 1.5~3초(4060 Ti, 8bit)면 약 400~750시간으로 추정된다.
- **결정**: 방법을 바꾸지 않는 **배치 추론(vLLM 등)을 먼저 적용**하고, pilot test에서 실제 속도를 잰 뒤 필요할 때만 아래 순서로 줄인다.
  1. 배치 추론: 프롬프트와 프레임이 같으므로 결과가 같고, 방법 변경이 없다.
  2. 프레임 간격 0.5초 → 1초: 시간이 절반이 되지만 논문 조건과 달라지고 When 정밀도가 떨어진다.
  3. 영상 수 1,520개 → 충돌 유형·주야 층화 표본 약 500개
- **pilot test 구성**
  - 원본: test split에서 충돌 유형·주야로 층화 추출한 **100개**
  - 열화: 그중 50개에 세 요인의 **L3만** 적용(3개 조건)
  - 호출 수는 약 1.5만 회(100×60 + 50×3×60)이고, L4 기준 약 3시간이다.
- **통과 기준**
  - **재현**: 원본 When(σ = 1초)이 논문 수치 0.343에 근접해야 한다. 크게 벗어나면 전체 실험 전에 설정(프롬프트, 양자화, 프레임 추출)을 점검한다.
  - **속도**: 측정한 호출 속도로 계산한 전체 예상 시간이 **GPU 100시간 이내**여야 한다. 넘으면 위 1 → 2 → 3 순서로 줄인다.
  - **열화 효과**: 각 요인의 L3에서 원본 대비 성능 저하가 관찰되어야 한다. 압축 L3의 저하가 거의 없으면 CRF 35 / 41 / 47로 강화한다(6번 예비안).
- **이유**
  - 전체를 돌리기 전에 재현 실패, 시간 초과, 열화 무효과라는 세 가지 위험을 약 3시간 안에 걸러낼 수 있다.
  - L3만 쓰는 이유: 효과가 가장 큰 단계에서도 저하가 없으면 L1·L2는 볼 필요가 없다.
  - 100시간 기준은 Colab Pro 2~3개월치이거나 집 PC로 약 2주(하루 8시간)에 해당하는 현실적인 상한이다.

## 제외 사항과 이유

### 저조도(Low Light)

- **재현성 문제**: 밝기·감마를 낮추는 합성 방식으로는 실제 야간 CCTV의 특징(센서 노이즈 증가, 가로등·헤드라이트 번짐, 자동 노출과 적외선 모드 전환)이 재현되지 않는다. 그래서 합성 저조도가 실제 야간 환경을 대표한다고 주장하기 어렵다.
- **요인 간 혼재**: 실제 저조도는 노이즈와 모션 블러(긴 노출)를 함께 일으킨다. 단독 요인으로 분리하면 모션 블러 조건과 효과가 겹친다.
- **범위 관리**: 지도교수 권고(대표 열화 요인 2~3개)를 넘지 않게 한다. 4종으로 늘리면 조건이 10개에서 13개로, 추론 시간이 약 30% 늘어난다.
- **대체 방안**: test split에 **실제 야간 영상 486개**가 있다. 합성 대신 주간/야간 하위 그룹 분석으로 저조도의 영향을 간접적으로 본다. 추가 추론이 필요 없다.
